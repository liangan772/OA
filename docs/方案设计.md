# CROA 方案设计（v0.1 讨论稿）

> 目标：以「编制」为统一底座，用一套通用节点驱动四类流程，并承载三类业务应用。

---

## 一、对需求的理解

### 1. 一个底座

「编制」是全系统的唯一组织事实来源：单位 → 部门 → 编制位 → 任职人员。
它同时决定四件事：

| 用途 | 说明 |
|---|---|
| 组织归属 | 谁在哪个部门、部门的上级是谁 |
| 表态人员生成 | 表态节点的参与人由编制规则自动推导，不手工勾选 |
| 一票否决判定 | 判断表态人是否占据本部门「负责人」编制位 |
| 数据权限 | 本人 / 本部门 / 本部门及下级 / 全单位 |

### 2. 两套系统，一个引擎

- **流程系统**：审议（自由发起）、审批（自动发起 / 自动接报）、执行、公示。
- **业务系统**：协调文档、邮件管理、收集表。
- 二者共用同一套编制、同一套节点实现、同一套待办与消息。业务对象（一份文档、一封邮件、一张收集表）也可以挂到流程上流转。

### 3. 「所有流程共用一套节点」

节点是**能力组件**，不是流程里的固定环节。系统内置六种节点类型，每个流程模板通过编排节点、并覆盖节点配置来组装自己的流程；内容模板（表单）与节点解耦，可自定义、可复用。

### 4. 六类节点语义

| 节点 | 本质 | 关键行为 |
|---|---|---|
| 表态节点 | 群体决策 | 按编制规则生成 N 个表态任务；部门负责人一票否决 |
| 总结节点 | 收敛结论 | 汇总表态明细，按规则或人工给出结论码 |
| 上报节点 | 跨级上行 | 在上级组织生成「审批流程」实例，本实例挂起等待回传 |
| 返回节点 | 跨级下行 | 把流程退回到下级的上报节点，下级可修改后重新上报 |
| 分配节点 | 任务派发 | 分配给部门或个⼈，部门级分配由负责人接单并可再派 |
| 执行节点 | 落地确认 | 必须「确认」并填写执行说明意见，可传附件 |

**上报 / 返回是本系统最核心的设计点**：它让审议流程和审批流程不是两条孤立流程，而是一棵**流程实例树**。下级审议的上报节点 → 生成上级审批实例（child）→ 上级审批的返回节点 → 唤醒下级上报节点（parent）。审批流程的「自动发起」正是由此触发，无需人工再建单。

## 二、领域模型

### 2.1 编制域（多级单位 + 跨单位协同）

单位与部门放在**同一棵组织树**里，用 `type` 区分，用 `rootUnitId` 标记归属单位。这样「上报沿树向上」一个算法就能同时穿透部门边界和单位边界。

```
Org(组织节点)
  id, code, name
  type        UNIT | DEPARTMENT | SECTION
  parentId    上级节点（部门的上级可以是部门，也可以是本单位；单位的上级是上级单位）
  rootUnitId  所属单位（UNIT 节点指向自己）
  path        物化路径 "/1/5/12/"（前缀匹配取整棵子树，免递归查询）
  level, sort, status

Position(编制位)
  id, orgId, code, name, duty, rank
  isLeader    是否本部门/本单位正职负责人位（唯一）
  isDeputy    是否副职
  headcount   定编数

Post(任职)  userId, positionId, isPrimary, startAt, endAt
User(人员)  account, passwordHash, name, phone, title, status
```

- 一个组织节点有且仅有一个 `isLeader = true` 的正职编制位，副职位若干。
- 人员归属由「任职」推导，不直接存 `orgId`；调动 = 改任职记录，历史流程仍指向发起时的编制快照。
- 编制台账：`定编数 / 实配数 / 空缺`，超编时任职操作给出警告而非阻断。

**跨单位协同**需要三层机制，缺一层就会在真实场景里卡住：

| 机制 | 作用 | 落点 |
|---|---|---|
| 跨单位寻址 | 上报能穿过单位边界找到上级单位的对应部门 | Org.path 前缀匹配 + 单位映射规则 |
| 跨单位授权 | A 单位可向 B 单位派单/会签，需显式授权，不能默认全通 | `CrossUnitGrant` 表 |
| 跨单位可见性 | 跨单位任务的参与人只能看到任务本身，不能翻对方单位的流程列表 | 数据权限按 `rootUnitId` 隔离，任务级例外放行 |

```
CrossUnitGrant
  id, grantorOrgId, granteeOrgId, scope(FLOW|DOC|COLLECT), flowTypes[], 
  expireAt, grantedBy, status
```

寻址规则（按优先级，模板可配）：`直接指定部门` → `上级单位同名部门`（如「办公室」对「办公室」）→ `上级单位默认接报部门` → `上级单位办公室` → 找不到则流程进入 `ADDRESS_FAILED` 并告警，不静默失败。

### 2.2 流程域

```
NodeDefinition(节点定义·全局)
  id, type, name, configSchema(JSON), defaultConfig, version

ContentTemplate(内容模板)
  id, name, schema(JSON Schema 表单), layout(打印/展示版式), version

FlowDefinition(流程模板)
  id, code, name, type(DELIBERATE|APPROVE|EXECUTE|PUBLICITY)
  contentTemplateId, status, version
  startRule(谁能发起 / 自动发起触发器)
  nodes: FlowDefinitionNode[]  nodeKey, nodeType, name, config, nextNodeKey

FlowInstance(流程实例)
  id, definitionId, definitionVersion, title, status
  formData(JSON), orgId, initiatorId
  parentInstanceId, originNodeInstanceId, rootInstanceId
  currentNodeKey

NodeInstance(节点实例)
  id, instanceId, nodeKey, nodeType, status, configSnapshot, result(JSON)
  startedAt, finishedAt, round(第几轮，供返回重入)

Task(待办)
  id, nodeInstanceId, assigneeId, assigneeOrgId, status
  action(AGREE|DISAGREE|ABSTAIN|CONFIRM|RETURN|PASS...), opinion, attachments
  deadline, finishedAt, version(乐观锁)

FlowLog(流转日志)  instanceId, nodeInstanceId, actorId, action, detail, createdAt
```

`configSnapshot` 很重要：流程模板改版后，在途实例仍按发起时的配置走。

### 2.3 业务域

```
Document(协调文档)   title, content, ownerOrgId, collaborators[], flowInstanceId?
DocVersion            docId, version, content, authorId
Mail                  subject, body, senderId, flowInstanceId?
MailRecipient         mailId, userId, type(TO|CC), readAt
CollectForm(收集表)   title, schema, scope(下发范围), deadline, flowInstanceId?
CollectResponse       formId, orgId, userId, data, submittedAt
Attachment            业务类型, 业务id, fileId, name, size
```

## 三、流程引擎设计

### 3.1 节点执行契约

每个节点类型实现同一套接口，引擎只认接口不认类型：

```ts
interface NodeHandler {
  type: NodeType
  // 进入节点：可能生成待办、可能生成子流程、可能直接完成
  onEnter(ctx: NodeContext): Promise<EnterResult>
  // 任务完成：更新节点状态，决定节点是否完成
  onTaskComplete(ctx: NodeContext, task: Task, input: TaskInput): Promise<void>
  // 节点达成结论，产出传给下游的数据
  onLeave(ctx: NodeContext): Promise<NodeOutcome>
  // 被返回节点退回时的处理
  onRejectBack?(ctx: NodeContext, reason: string): Promise<void>
}
```

引擎主循环：

```
advance(instance):
  node = current
  while node is auto-completable:
     outcome = handler.onLeave(node)
     if outcome == GOTO(next) -> node = next
     if outcome == WAIT       -> break（等人 / 等子流程）
     if outcome == END        -> 实例终态，回调 parent
```

### 3.2 一票否决规则（需确认）

- 表态人集合中包含本部门负责人 → 其 `DISAGREE` 即判定节点结论 `VETOED`，立即关闭其余未完成表态任务（记「因否决终止」）。
- 否决记录独立留痕：`vetoedBy`、否决意见，流程详情页醒目展示。
- 需确认的边界：
  1. 负责人本人是否一定进入表态人集合（建议：是，且不可被规则排除）。
  2. 负责人未表态（超时）算弃权还是默认同意（建议：弃权，且**不**触发否决）。
  3. 否决后是「直接终止」还是「退回上一节点/发起人修改」（建议：模板可配，默认终止）。
  4. 副职负责人是否有否决权（建议：仅正职）。

### 3.3 总结节点的结论规则

可选：`ALL_AGREE`（全票）、`MAJORITY`（多数）、`LEADER_DECIDE`（负责人裁定）、`MANUAL`（总结人填写）。
总结人本身也由编制规则产生（如：本部门负责人、办公室秘书岗）。

### 3.4 上报 / 返回的联动机制

```
下级审议实例 A
  ... → [上报节点 R]  status = WAITING
            │ 创建 B = approve 模板实例, B.parentInstanceId = A, B.originNodeInstanceId = R.instance
            ▼
        上级审批实例 B
          ... → [表态] → [总结] → 分支
                    ├─ 通过 → [公示/执行] → B 终态(APPROVED) → 回调 R
                    └─ 不通过 → [返回节点] → 写回 A
                                              A.R 收到 RETURNED
                                              A 回到 R 之前的可编辑节点，round+1
                                              重新上报时复用同一个 B 还是新建？→ 建议新建轮次实例，保留历史
```

- 上报寻址按 2.1 的五级规则逐级回退，跨单位时以 `rootUnitId` 变化为边界。
- 返回携带：结论码、意见、批注（可对表单字段逐项批注）。
- 重试上限 `maxRound`（默认 3），超限转「异常终止」并通知发起人。

### 3.5 实例状态机

`DRAFT → RUNNING → (WAITING) → APPROVED | REJECTED | VETOED | RETURNED | TERMINATED | ARCHIVED`
任意非终态可 `WITHDRAW`（发起人撤回，仅限首节点未完成时）。

## 四、技术架构

### 4.1 选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite + Ant Design 5 | 中后台组件最全，表单/表格/树开箱可用 |
| 后端 | NestJS 10 + TypeScript | 模块化契合「多域」；DI 便于节点注册表 |
| ORM | Prisma 5 | 类型安全，schema 单一事实来源 |
| 数据库 | PostgreSQL 16 | JSONB 存表单与节点快照；物化路径前缀查询高效 |
| 缓存 / 锁 | Redis 7 | 流程推进互斥锁、登录限流、待办计数缓存；不可用时自动降级直通 |
| 鉴权 | JWT + 编制数据权限 | 权限点与组织范围分离 |
| 文件 | 本地磁盘（可切 S3/MinIO） | 抽象 StorageProvider |
| 部署 | Docker Compose（postgres + redis + server + nginx） | 内网单机一键起，前端 Nginx 反代 `/api` |

### 4.2 目录结构

```
oooa/
├─ packages/
│  ├─ shared/        共享类型、节点 config schema、常量
│  ├─ server/
│  │  ├─ src/modules/auth
│  │  ├─ src/modules/org        编制
│  │  ├─ src/modules/template   内容模板
│  │  ├─ src/modules/flow
│  │  │   ├─ engine/            引擎主循环
│  │  │   ├─ nodes/             vote|summarize|report|return|assign|execute
│  │  │   └─ api/
│  │  ├─ src/modules/doc
│  │  ├─ src/modules/mail
│  │  ├─ src/modules/collect
│  │  └─ src/modules/common     权限、审计、通知、文件
│  └─ web/
│     ├─ src/pages/workbench    我的待办/已办/我发起
│     ├─ src/pages/flow         发起/详情/时间线
│     ├─ src/pages/design       流程设计器 + 表单设计器
│     ├─ src/pages/org          编制管理
│     └─ src/pages/biz          文档/邮件/收集表
├─ docs/
└─ docker/
```

### 4.3 引擎事务与可靠性

- 一次「完成任务」= 一个数据库事务：更新 Task → 推进 NodeInstance → 生成下游 Task / 子实例 → 写 FlowLog → 写 Notification（事务后异步发）。
- Task 乐观锁 `version`，重复提交返回 409，天然幂等。
- 定时任务（10 min）：超时催办、超时自动表态（按配置）、实例超期预警。

### 4.4 关键页面

1. **工作台**：待办（含一票否决醒目标记）、已办、我发起、抄送我的。
2. **流程详情**：左侧表单（可折叠），右侧节点进度时间线 + 表态矩阵（谁同意/反对/未表）+ 一票否决横幅。
3. **流程设计器**：节点拖拽、连线、每节点配置抽屉（配置项由节点 configSchema 驱动，前端自动生成表单）。
4. **表单设计器**：字段拖拽，产出 JSON Schema；支持单行/多行/数字/日期/下拉/附件/明细表/富文本。
5. **编制管理**：组织树 + 编制位台账（定编/在编/空缺）+ 任职调整。

## 五、实施分期

| 阶段 | 内容 | 产出 |
|---|---|---|
| M1 地基 | 工程骨架、鉴权、编制域 CRUD、RBAC、工作台壳 | 可登录，能维护组织与人员 |
| M2 流程内核 | 引擎、六类节点、内容模板、实例与待办 | 能跑通单部门「表态→总结」 |
| M3 跨级联动 | 上报/返回、实例树、审批自动发起、四类流程模板 | 两级部门完整闭环 |
| M4 业务系统 | 协调文档、邮件、收集表 | 三件套可用且可挂流程 |
| M5 打磨交付 | 设计器、通知、审计、报表、Docker、单元测试、README、推 GitHub | 可交付版本 |

每阶段结束提供可运行版本 + 变更说明，避免一次性交付黑箱。

**待定（我先按括号内默认值实现，你随时可改）：**

1. 负责人未表态（超时）→ 视为弃权，**不**触发否决。

3. 副职负责人 → 无否决权，仅正职。
4. 上报重试上限 `maxRound` → 3 次，超限转异常终止。
